Тестирование

Unit, fragments, screenshot, e2e

Илья Степанов

Что такое тестирование

Проверка, что код работает так, как мы ожидаем

Можно руками. Можно автоматически. Автотесты дешевле повторять.

Зачем автотесты

  • Регрессии - старые сценарии перепроверяются на каждый коммит
  • Рефакторинг без страха - тесты ловят сломанное поведение
  • Документация - тест показывает, как пользоваться кодом
  • Обратная связь - секунды вместо минут ручной проверки

  • Стоимость поддержки
  • Плохие тесты ломаются на любой рефакторинг

Пирамида тестов

e2e - мало, дорого, медленно
integration / screenshot
unit - много, дёшево, быстро

Чем выше уровень - тем медленнее и нестабильнее. Базу пишем юнитами.

Часто всё это - один пакет. Но под капотом это разные слои.

Jest

Стандарт-де-факто 2017–2022. От Facebook, всё в одном.

  • Runner + assertions + mocks + jsdom из коробки
  • Огромная экосистема, тысячи примеров
  • Snapshot-тесты прямо в API
  • CommonJS-наследие, проблемы с ESM
  • Медленнее современных аналогов

Пример теста на Jest

describe('sum', () => {
  it('складывает два числа', () => {
    expect(sum(2, 3)).toBe(5);
  });

  it('кидает на нечислах', () => {
    expect(() => sum('a', 1)).toThrow(TypeError);
  });
});

describe - группа, it - тест, expect - проверка. Этот же API повторяет почти каждая современная библиотека.

Vitest

Тот же API, что у Jest, но из коробки с Vite и ESM

  • Быстрый - общий dev-сервер с Vite
  • Нативный ESM, TypeScript без настройки
  • Watch-режим перерисовывает только затронутые тесты
  • UI-режим: смотришь тесты в браузере
  • Если проект на Vite - выбор очевиден

Jest vs Vitest

Jest Vitest
Конфиг jest.config.js + babel vite.config.ts (общий)
ESM через --experimental-vm-modules нативно
TypeScript ts-jest / babel встроенный esbuild
Скорость холодного старта ~ медленнее ~ в 2–5 раз быстрее
API describe/it/expect тот же + vi.fn()
Экосистема огромная, всё совместимо растёт, jest-плагины часто работают

Mocha + Chai

Старая школа: runner отдельно, assertions отдельно

// Mocha - runner
// Chai - assertions
import { expect } from 'chai';

describe('Array', () => {
  it('.indexOf возвращает -1 для отсутствующих', () => {
    expect([1, 2, 3].indexOf(4)).to.equal(-1);
  });
});

Гибкость ценой количества зависимостей. Сейчас выбирают редко.

node:test

Встроенный test runner в Node 20+

import { test } from 'node:test';
import assert from 'node:assert/strict';

test('сумма', () => {
  assert.equal(sum(2, 3), 5);
});
  • Ноль зависимостей
  • Быстрый старт для бэкенда / CLI
  • Нет jsdom - DOM-тесты не подойдут

Mocking

Подменяем зависимости, чтобы тест оставался изолированным

// vi.fn() / jest.fn() - мок-функция
const onClick = vi.fn();
button.click();
expect(onClick).toHaveBeenCalledOnce();
expect(onClick).toHaveBeenCalledWith({ id: 1 });

Сетевые запросы - не мокаем fetch вручную, а используем MSW (Mock Service Worker).

MSW - мокаем сеть честно

import { http, HttpResponse } from 'msw';
import { setupServer } from 'msw/node';

const server = setupServer(
  http.get('/api/users', () =>
    HttpResponse.json([{ id: 1, name: 'Аня' }])
  )
);

beforeAll(() => server.listen());
afterAll(() => server.close());

Перехват на уровне сети - код приложения думает, что общается с реальным API.

@testing-library/react

Тестируем компонент так, как видит пользователь

  • Поиск по роли / тексту, а не по className
  • userEvent эмулирует реальный ввод
  • Тесты не ломаются от рефакторинга разметки
  • Лозунг: «не тестируй внутренности - тестируй поведение»

Пример теста компонента

import { render, screen } from '@testing-library/react';
import userEvent from '@testing-library/user-event';

it('увеличивает счётчик по клику', async () => {
  render();
  const btn = screen.getByRole('button', { name: '+' });

  await userEvent.click(btn);
  await userEvent.click(btn);

  expect(screen.getByText('Счёт: 2')).toBeInTheDocument();
});

Enzyme

Библиотека от Airbnb, доминировала в React-мире 2016–2019

  • Три способа рендера: shallow, mount, render
  • jQuery-подобный API: .find(), .props(), .state(), .simulate()
  • Можно было лезть прямо в внутренности компонента

Пример теста на Enzyme

import { shallow } from 'enzyme';

it('увеличивает счётчик по клику', () => {
  const wrapper = shallow();

  expect(wrapper.state('count')).toBe(0);
  expect(wrapper.find('.label').text()).toBe('Счёт: 0');

  wrapper.find('button').simulate('click');

  expect(wrapper.state('count')).toBe(1);
  expect(wrapper.find('.label').text()).toBe('Счёт: 1');
});

Тест читает state компонента напрямую и кликает по селектору button.

Shallow vs Mount

shallow

Рендер только текущего компонента, дочерние - заглушки. Быстро, но не видит реальное дерево.

mount

Полный рендер с детьми и lifecycle. Ближе к реальности, медленнее.

shallow поощрял тестирование изоляции - но мокал реальное поведение детей.

Enzyme - почему ушли

  • Лез во внутренности React: state, props, экземпляры
  • Тесты ломались при любом рефакторинге компонента
  • Нет официальной поддержки React 18+
  • Перешли на @testing-library - она тестирует поведение

Playwright Component Testing

Юнит-тест компонента в реальном браузере, а не в jsdom

Component.tsx
→
Chromium / Firefox / WebKit
→
Locator API
  • Настоящий браузер - настоящие layout, fonts, события
  • Тот же API, что и в e2e - один навык на всё
  • Медленнее Vitest+jsdom - нужен браузер

Пример Playwright CT

import { test, expect } from '@playwright/experimental-ct-react';
import { Counter } from './Counter';

test('увеличивает счётчик по клику', async ({ mount }) => {
  const component = await mount();

  await expect(component.getByText('Счёт: 0')).toBeVisible();
  await component.getByRole('button', { name: '+' }).click();
  await expect(component.getByText('Счёт: 1')).toBeVisible();
});

mount рендерит компонент в браузере и возвращает Locator - тот же, что в e2e.

jsdom vs реальный браузер

Vitest + jsdom Playwright CT
Окружение эмуляция DOM в Node настоящий Chromium
CSS layout нет - getBoundingClientRect = 0 работает
Скорость миллисекунды сотни мс
Скриншоты нет да, прямо в тесте компонента
API теста describe / it / expect тот же, что в e2e

Проект Выбор
Новый Vite-проект Vitest + @testing-library
Существующий CRA / Next Jest + @testing-library
Бэкенд / CLI / библиотека node:test или Vitest
Компонент с layout / CSS-логикой Playwright Component Testing
Сетевые запросы + MSW
Старый код с Enzyme миграция на @testing-library

Проблема грязных тестов

it('добавляет строку в список', async () => {
  const { container } = render();
  const input = container.querySelector('.Input');
  await userEvent.type(input, 'Хлеб');
  await userEvent.click(container.querySelector('.Add'));

  const rows = container.querySelectorAll('.Row');
  expect(rows[0].querySelector('.Row-Name').textContent).toBe('Хлеб');
});

Селекторы расползлись по 50 тестам. Поменяли className - упало всё.

Идея Fragment

Класс-обёртка над DOM-узлом компонента. Знание о разметке живёт в одном месте.

DOM-узел
Element
→
Fragment
геттеры + методы
→
Тест
читаемый код

BaseObject

import userEvent from '@testing-library/user-event';

export class BaseObject {
  container: Element;

  constructor(container: Element) {
    this.container = container;
  }

  async click() {
    await userEvent.click(this.container);
  }
}

Все fragments наследуют это: умеют хранить свой узел и кликаться.

RowObject - конкретный fragment

export class RowObject extends BaseObject {
  get text() {
    return this.container
      .querySelector('.Row-Name')?.textContent || '';
  }

  get deleteButton(): BaseObject {
    const el = this.container.querySelector('.Row-Remove')!;
    return new BaseObject(el);
  }
}

Геттеры: примитив (текст) или вложенный fragment.

AppObject - композиция

export class AppObject {
  constructor(public container: Element) {}

  get rows(): RowObject[] {
    return Array.from(this.container.querySelectorAll('.Row'))
      .map(row => new RowObject(row));
  }

  get rowsNames(): string[] {
    return this.rows.map(r => r.text);
  }

  async inputType(text: string) {
    await userEvent.type(this.input, text);
  }

  private get input(): Element {
    return this.container.querySelector('.Input')!;
  }

  get addButton(): BaseObject {
    return new BaseObject(this.container.querySelector('.Add')!);
  }
}

Тест с fragment'ом

it('добавляет строку в список', async () => {
  const { container } = render();
  const app = new AppObject(container);

  await app.inputType('Хлеб');
  await app.addButton.click();

  expect(app.rowsNames).toEqual(['Хлеб']);
});

Тест читается как сценарий: ввести → нажать → проверить. Ни одного querySelector.

Что мы выиграли

  • Селекторы - в одном месте. Меняем разметку - правим один класс
  • Тесты читаются как пользовательский сценарий
  • Композиция: AppObject состоит из RowObject[]
  • Один и тот же fragment работает в unit, скриншотных и e2e
  • Fragment = Page Object на уровне компонента

Скриншотные тесты

Зачем?

Юниты не видят, что кнопка стала розовой и съехала на 200px вправо

Скриншотные тесты ловят визуальные регрессии

Идея

Render
→
Скриншот
→
Diff с эталоном
→
Pass / Fail

Первый прогон - сохраняем эталон. Дальше каждый тест сравнивается с ним.

Инструменты

  • Playwright - toHaveScreenshot из коробки
  • Hermione → Testplane - Yandex, на базе WebdriverIO
  • Chromatic - облако + Storybook
  • Percy - облачный сервис diff'ов
  • Loki - Storybook + локальный Docker

Playwright

test('главная страница', async ({ page }) => {
  await page.goto('/');
  await expect(page).toHaveScreenshot('home.png');
});
  • Встроено, без плагинов
  • --update-snapshots для перегенерации эталонов
  • Trace viewer показывает diff наглядно
  • Эталоны привязаны к ОС - проблема при разработке на mac/win + linux в CI

Hermione → Testplane

Скриншотный фреймворк от Яндекса. В 2024 переименован в Testplane.

it('шапка', async ({ browser }) => {
  await browser.url('/');
  await browser.assertView('header', '.Header');
});
  • Скриншот по селектору, а не всей страницы
  • Browser pool, ретраи, параллелизация из коробки
  • html-reporter - удобный UI с diff'ами
  • Плагины: Storybook, OAuth, тестовые данные

Playwright vs Testplane

Playwright Testplane
Под капотом свой протокол CDP WebdriverIO + Selenium grid
Скриншот страница / элемент по селектору, элемент
Репорт встроенный + trace html-reporter (отдельный)
Фокус универсальный e2e скриншоты + e2e
Сообщество огромное, мировое сильное в РФ

Проблема нестабильности

  • Анимации - кадр не тот, что в эталоне
  • Шрифты подгружаются асинхронно
  • Date.now() / Math.random() - каждый раз разное
  • Скроллбары / курсор / выделение текста
  • Сабпиксельный рендер - разные ОС, разные GPU

Как стабилизировать

  • Отключить анимации: * { animation: none !important }
  • Замокать дату и рандом
  • Дождаться загрузки шрифтов: document.fonts.ready
  • Фикстуры - те же данные на каждый прогон
  • Threshold - допускаем 0.1% разницы пикселей
  • CI на той же ОС, что и эталон (обычно linux в Docker)

Storybook

Среда для разработки UI-компонентов в изоляции от приложения

Запускается отдельным сервером. Каталог всех компонентов проекта со всеми их состояниями - живая дизайн-система прямо в браузере.

Зачем

  • Разрабатываем компонент без запуска всего приложения
  • Видим все состояния сразу: loading / disabled / error / hover
  • Документация для команды и дизайнеров - единая точка правды
  • Быстрая разработка: hot-reload только компонента
  • Точка входа для скриншотных и a11y-тестов

Story - одно состояние компонента

// Button.stories.tsx
import { Button } from './Button';

export default {
  title: 'UI/Button',
  component: Button,
};

export const Primary = {
  args: { variant: 'primary', children: 'Купить' },
};

export const Loading = {
  args: { variant: 'primary', loading: true, children: 'Купить' },
};

export const Disabled = {
  args: { variant: 'primary', disabled: true, children: 'Купить' },
};

Файл рядом с компонентом. Storybook собирает все *.stories.tsx в каталог.

Что даёт Storybook поверх

  • Args / Controls - крутилки для props прямо в браузере
  • Actions - логирование вызовов onClick и других обработчиков
  • Docs - автоматическая страница с props-таблицей
  • Addons - a11y, viewport, темы, i18n
  • Play function - сценарий взаимодействия для каждой story

Когда не надо

  • Чисто бизнес-логика - юниты быстрее
  • Динамический контент без эталонов (фиды, ленты)
  • Очень частые визуальные правки - слишком дорого обновлять эталоны
  • Лучше всего: дизайн-система и стабильные экраны

E2E Тесты

Что такое e2e

Реальный браузер
↔
Реальное приложение
↔
Реальный бэкенд
↔
Реальная БД

Проверяем сценарий целиком - от клика пользователя до записи в базу.

Unit / Integration / E2E

Unit Integration E2E
Что проверяем функцию / компонент несколько модулей сценарий пользователя
Сеть замокана часто замокана реальная
Браузер jsdom jsdom настоящий Chromium
Скорость миллисекунды секунды минуты
Стабильность высокая средняя низкая (flaky)

Инструменты

  • Playwright - Microsoft, мульти-браузерный, мульти-таб
  • Cypress - самый удобный DX, time-travel debugger
  • WebdriverIO - селениум-based, гибкий
  • Testplane - то же, плюс скриншоты
  • Selenium - старый, но всё ещё стандарт в QA-командах

Cypress vs Playwright

Cypress Playwright
Архитектура тесты внутри браузера тесты управляют браузером по CDP
Несколько вкладок нет да
Несколько origin'ов проблематично штатно
Браузеры Chromium, Firefox, Edge + WebKit (Safari)
UI-режим сильнейший в индустрии хороший trace viewer
Скорость средняя выше

Пример сценария на Playwright

test('покупка товара', async ({ page }) => {
  await page.goto('/');
  await page.getByRole('link', { name: 'Войти' }).click();
  await page.getByLabel('Email').fill('test@x.com');
  await page.getByLabel('Пароль').fill('secret');
  await page.getByRole('button', { name: 'Войти' }).click();

  await page.getByRole('link', { name: 'Хлеб' }).click();
  await page.getByRole('button', { name: 'В корзину' }).click();
  await page.getByRole('link', { name: 'Корзина' }).click();

  await expect(page.getByText('Итого: 50 ₽')).toBeVisible();
});

Селекторы - приоритет

  • getByRole - как видит скринридер. Лучшее
  • getByLabel / getByText - как видит пользователь
  • data-testid - когда нет роли (декоративные элементы)
  • .css-selector и className - последнее средство

Page Object

export class LoginPage {
  constructor(private page: Page) {}

  async goto() {
    await this.page.goto('/login');
  }

  async login(email: string, password: string) {
    await this.page.getByLabel('Email').fill(email);
    await this.page.getByLabel('Пароль').fill(password);
    await this.page.getByRole('button', { name: 'Войти' }).click();
  }
}

Тот же подход, что fragments - но обёртка вокруг Playwright Page.

Flaky-тесты - главная боль

Тест зелёный 9 раз из 10 и красный на десятый

  • Гонки: тест проверяет до того, как контент подгрузился
  • Анимации, transitions, debounce
  • Сторонние сервисы - реклама, аналитика
  • Изменчивые данные - заказы, остатки на складе

Борьба с flakiness

  • Auto-waiting в Playwright/Cypress - не sleep, а ожидание условия
  • Retries в CI: 1–2 повтора при падении
  • Изолированные данные - каждый тест создаёт свои
  • Моки внешних API через сеть (Playwright route)
  • Никаких setTimeout в ожиданиях

Тестовые данные

  • Seed - наполнение БД фикстурами перед прогоном
  • Per-test setup - каждый тест создаёт пользователя через API
  • Транзакции - откат БД после теста
  • Network mocks - внешние API подменяем

Параллелизация и шардирование

100 тестов
→
4 шарда × 5 воркеров
→
~5 минут

Шарды - параллельные runner'ы в CI. Воркеры - параллельные браузеры внутри одного runner'а. Условие: тесты не делят состояние.

Запуск в CI

  • Headless-режим - без UI, быстрее
  • Видеозапись и trace для упавших тестов
  • Артефакты в PR: видео, скриншоты, html-репорт
  • Docker-образ с фиксированной версией браузера
  • Smoke-набор на каждый коммит, полный - ночью

Сколько e2e писать

Пирамида:Много unit, мало e2e. e2e - только критичные сценарии.

В реальности: 5–20 e2e на критичные сценарии (логин, оплата, регистрация).

Главное

  • Тестируйте поведение, а не внутренности
  • Селекторы - в одном месте (Fragment / Page Object)
  • Юнитов много, e2e мало - но они должны быть
  • Падающий тест - это хорошо. Молчаливый прод - плохо
