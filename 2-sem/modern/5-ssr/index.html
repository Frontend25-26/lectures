Что страдает

FCP

First Contentful Paint запаздывает - контент появляется только после выполнения JS
SEO

og-теги

Медленный канал

Когда SPA достаточно

  • Внутренние инструменты - CRM, дашборды, админки
  • Приложения за авторизацией - SEO не нужен
  • Интерактивные редакторы - figma-like, IDE-like

  • Публичный сайт с контентом - лендинг, блог, каталог
  • Страницы, которые шарят в соцсетях
  • E-commerce с SEO-трафиком

Способы рендеринга

CSR - Client-Side Rendering

Сервер
->
Пустой HTML
->
Браузер рендерит

Сервер отдаёт пустую HTML-оболочку и весь JS-бандл. Браузер скачивает его, выполняет и только тогда строит DOM - вся логика рендера живёт на устройстве пользователя.

  • Мгновенные переходы после загрузки
  • Дешёвый хостинг - только статика
  • Медленный первый экран
  • SEO проблемы
  • React create-react-app, Vite SPA

SSR - Server-Side Rendering

Запрос
->
Сервер рендерит HTML
->
Готовый HTML
->
Hydration

На каждый запрос сервер запускает React, получает данные и возвращает готовый HTML. Браузер показывает его сразу - без ожидания бандла. Потом JS подключается и «оживляет» интерактивность через hydration.

  • Быстрый FCP - пользователь сразу видит контент
  • SEO работает из коробки
  • Нужен сервер для каждого запроса
  • Сложнее с кешированием

SSG - Static Site Generation

Build time
->
HTML-файлы
->
CDN
->
Браузер

Все страницы генерируются один раз во время сборки и публикуются как статические файлы на CDN. Данные фиксируются на момент деплоя - живой сервер не нужен.

  • Максимально быстрый ответ - отдаёт CDN
  • SEO отличный
  • Дёшево
  • Данные актуальны только на момент сборки
  • Долгий rebuild при большом числе страниц
  • Блог, документация, лендинг

ISR - Incremental Static Regeneration

CDN
->
Stale-while-revalidate
->
Фоновый rebuild

Страницы генерируются статически, но перестраиваются автоматически через заданный интервал. Пока новая версия собирается в фоне, CDN отдаёт старую - компромисс между скоростью SSG и свежестью данных.

  • Скорость CDN + свежесть данных
  • Не нужно пересобирать весь сайт
  • Первый запрос после инвалидации отдаёт устаревшее
  • E-commerce: цены и остатки могут устаревать на несколько секунд

Когда что выбирать

Режим Когда данные меняются Нужен сервер Пример
CSR Всегда / real-time Нет Дашборд, чат
SSR При каждом запросе Да Профиль пользователя
SSG Редко (деплой) Нет Блог, документация
ISR Иногда (N секунд) Да Каталог товаров

Next.js SSR

Гидрация

Сервер отдаёт готовый HTML - пользователь видит контент сразу. Но HTML мёртвый - кнопки не работают, события не слушаются

Сервер
готовый HTML
-
Браузер
рисует HTML
-
Загружается JS
bundle.js
-
React «оживляет»
hydration
  • React повторно обходит дерево компонентов и присоединяет обработчики к уже существующему DOM
  • DOM при этом не перерисовывается - React доверяет HTML с сервера
  • До завершения гидрации кнопки видны, но не реагируют на клики

Ошибки гидрации

React сравнивает HTML с сервера с тем, что рендерит на клиенте. Если они расходятся - ошибка

Ошибки гидрации

// ❌ Классика: Date и Math.random()
const Page: FC = () => (
    <div>
        Сейчас: {new Date().toLocaleTimeString()}  {/* разное время на сервере и клиенте */}
        ID: {Math.random()}                        {/* разные числа */}
    </div>
);

// ❌ Секундомер - обновляется каждую секунду
const Timer: FC = () => {
    const [time, setTime] = useState(new Date().toLocaleTimeString());
    useEffect(() => {
        const id = setInterval(() => setTime(new Date().toLocaleTimeString()), 1000);
        return () => clearInterval(id);
    }, []);
    return <span>{time}</span>;  // сервер рендерит одно время, клиент - другое
};

Ошибки гидрации

// ✅ suppressHydrationWarning - React не сравнивает содержимое этого тега
const Timer: FC = () => (
    <span suppressHydrationWarning>
        {new Date().toLocaleTimeString()}
    </span>
);
  • Работает только на один уровень вложенности - дочерние теги не защищает
  • Подходит для значений, которые всегда будут разными: время, случайные ID
  • Альтернатива - dynamic(..., { ssr: false }) для полного отключения SSR компонента
// page.tsx - загружаем Timer только на клиенте
import dynamic from 'next/dynamic';

const Timer = dynamic(() => import('./Timer'), { ssr: false });

export default function Page() {
    return <div>Текущее время: <Timer /></div>;
}

Pages Router - как было раньше

До App Router данные получали через специальные функции на уровне страницы 

// pages/products.tsx - SSR: выполняется на каждый запрос
export async function getServerSideProps() {
    const products = await fetch('https://api.example.com/products').then(r => r.json());
    return { props: { products } };  // обязательно обернуть в { props }
}

const ProductsPage: FC<{ products: Product[] }> = ({ products }) => <List items={products} />;

// pages/blog/[slug].tsx - SSG + ISR
export async function getStaticProps({ params }) {
    const post = await getPost(params.slug);
    return { props: { post }, revalidate: 60 };  // перестраивать каждые 60с
}

export async function getStaticPaths() {
    return { paths: [...], fallback: 'blocking' };
}

App Router убрал эти функции - данные теперь получают прямо в async-компоненте

Серверные компоненты

В App Router все компоненты серверные по умолчанию 

// app/products/page.tsx - серверный компонент
// async/await без useEffect, fetch прямо здесь
const ProductsPage: FC = async () => {
    const products = await fetch('https://api.example.com/products').then(r => r.json());

    return (
        <ul>
            {products.map(p => <li key={p.id}>{p.name}</li>)}
        </ul>
    );
}
export default ProductsPage;

Этот код выполняется только на сервере - в браузер уходит готовый HTML

"use client"

Директива в начале файла - переключает компонент в клиентский режим 

'use client';

import { useState } from 'react';

const Counter: FC = () => {
    const [count, setCount] = useState(0);
    return <button onClick={() => setCount(c => c + 1)}>{count}</button>;
}
export default Counter;

Когда ставить "use client":

  • Используете хуки - useState, useEffect, useRef
  • Обрабатываете события - onClick, onChange
  • Нужны браузерные API - localStorage, window

Ограничения компонентов

Серверный

  • Прямой доступ к БД
  • Секреты и env-переменные
  • async/await на верхнем уровне
  • Нельзя: хуки
  • Нельзя: обработчики событий
  • Нельзя: браузерные API

Клиентский

  • useState, useEffect
  • onClick, onChange
  • localStorage, window
  • Нельзя: прямой fetch к БД
  • Нельзя: секреты (попадут в бандл)
  • Нельзя: async компонент

Композиция компонентов

// Серверный оборачивает клиентский - ОК
const Page: FC = async () => {
    const data = await fetchData();
    return (
        <Layout>
            <ClientWidget data={data} />  {/* 'use client' */}
        </Layout>
    );
}

// Клиентский импортирует серверный - ОШИБКА
'use client';
import { ServerComponent } from './ServerComponent'; // ❌

const ClientWrapper: FC = () => {
    return <ServerComponent />;  // серверная логика попадёт в бандл
}

Серверные компоненты можно передавать как children - это работает

Получение данных

Вместо useEffect + useState - просто async компонент 

// Раньше (CSR):
const Products: FC = () => {
    const [data, setData] = useState(null);
    useEffect(() => {
        fetch('/api/products').then(r => r.json()).then(setData);
    }, []);
    if (!data) return <Spinner />;
    return <List items={data} />;
}

// Теперь (Next.js App Router):
const Products: FC = async () => {
    const data = await fetch('https://api.example.com/products').then(r => r.json());
    return <List items={data} />;
}

Кеширование и ревалидация

// По умолчанию - кешируется навсегда (SSG-поведение)
fetch('https://api.example.com/products');

// Не кешировать - SSR на каждый запрос
fetch('https://api.example.com/products', { cache: 'no-store' });

// Обновлять каждые N секунд - ISR-поведение
fetch('https://api.example.com/products', {
    next: { revalidate: 60 }  // раз в минуту
});

'use server'

Директива помечает функцию как серверную - она никогда не попадёт в клиентский бандл

На файл

// actions.ts
'use server';

// все экспорты - серверные
export async function createPost() { ... }
export async function deletePost() { ... }

На функцию

// прямо в серверном компоненте
const Page: FC = async () => {
    async function save(data: FormData) {
        'use server';
        await db.save(data);
    }
    return <form action={save}>...</form>;
}
  • Вызывается из клиентского компонента как обычная функция
  • Под капотом - POST-запрос к Next.js-серверу
  • Доступны: БД, файловая система, секреты из env

Зачем нужен 'use server'

Без него пришлось бы писать отдельный API-роут и вручную делать fetch

Без 'use server'

// 1. Создать app/api/posts/route.ts
export async function POST(req: Request) {
    const { title } = await req.json();
    await db.posts.create({ title });
    return Response.json({ ok: true });
}

// 2. Вызвать из клиента
const handleSubmit = async () => {
    await fetch('/api/posts', {
        method: 'POST',
        body: JSON.stringify({ title }),
    });
};

С 'use server'

// actions.ts
'use server';
export async function createPost(title: string) {
    await db.posts.create({ title });
}

// клиентский компонент
const handleSubmit = async () => {
    await createPost(title);  // просто вызов
};
  • Нет маршрута - нет URL - нет случайных прямых обращений
  • Аргументы сериализуются автоматически - не нужен JSON.stringify
  • TypeScript-типы работают сквозь границу клиент/сервер

Server Actions

Функции, которые выполняются на сервере - вызываются напрямую из компонента 

// actions.ts
'use server';

export async function createPost(formData: FormData) {
    const title = formData.get('title') as string;
    await db.posts.create({ title });
    revalidatePath('/posts');  // сбросить кеш страницы
}

// page.tsx - форма без API-роута
import { createPost } from './actions';

const NewPostPage: FC = () => (
    <form action={createPost}>
        <input name="title" placeholder="Заголовок" />
        <button type="submit">Создать</button>
    </form>
);
export default NewPostPage;

Server Actions - мутации

'use server';

export async function deletePost(id: string) {
    await db.posts.delete({ where: { id } });
    revalidatePath('/posts');
}

'use client';
import { deletePost } from './actions';

const PostCard: FC<{ post: Post }> = ({ post }) => (
    <div>
        <h3>{post.title}</h3>
        {/* Server Action вызывается как обычная функция */}
        <button onClick={() => deletePost(post.id)}>Удалить</button>
    </div>
);
export default PostCard;

Никакого API-роута, никакого fetch('/api/posts/delete')

Server Actions - когда не подходят

  • Бэкенд уже существует - отдельный сервис на Go / Python / Java
  • Разные клиенты - мобилка, другой фронтенд, сторонние сервисы не могут вызвать Server Action
  • Разные команды - нет явного контракта, нет OpenAPI, сложно разграничить ответственность
  • Тяжело тестировать - QA не могут легко тестировать работу Server Action, тк к доступ к ним только в коде
  • Авторизацию легко забыть - у HTTP-эндпоинта есть явная "граница входа", у Action - нет

Server Actions - отличный выбор для небольших fullstack-проектов.
В компаниях явный API остаётся стандартом.

Типичная ошибка

// ❌ "use client" везде
'use client';

// Этот компонент только отображает данные
// Никаких хуков, никаких событий
// Но "use client" поставили "на всякий случай"
const ProductCard: FC<{ product: Product }> = ({ product }) => (
    <div>
        <h3>{product.name}</h3>
        <p>{product.price} ₽</p>
    </div>
);
  • Компонент попадает в JS-бандл - увеличивает его размер
  • Нельзя использовать прямой доступ к БД или секреты
  • Вся поддерево становится клиентским

Правило: "use client" только там, где это необходимо

Граница клиент/сервер

// Правильная архитектура:
// Серверный компонент загружает данные,
// передаёт их в клиентские «острова» интерактивности

const ProductPage: FC<{ params: { id: string } }> = async ({ params }) => {
    const product = await db.products.findById(params.id);  // серверно
    return (
        <div>
            <ProductInfo product={product} />   {/* серверный */}
            <AddToCartButton id={product.id} /> {/* клиентский */}
            <Reviews productId={product.id} />  {/* серверный */}
        </div>
    );
}

«Острова» интерактивности - минимум клиентского JS, максимум серверного HTML
