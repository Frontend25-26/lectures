## Слайд 1 — React. Введение в библиотеку

Всем привет. Сегодня начинаем второй большой блок курса — JavaScript-фреймворки. И первая тема, которую мы разберём — это React.

Но прежде чем открывать первый файл с кодом, я хочу, чтобы вы поняли: зачем React вообще появился? Какую проблему он решает? Для этого нам нужно немного истории.

---

## Слайд 2 — Архитектуры фронтенда

Начнём с архитектур. За последние 20 лет фронтенд прошёл несколько принципиально разных подходов к тому, как строить веб-приложения. Мы разберём три из них: MPA, PEMPA и SPA. И на каждом этапе будем смотреть — что было хорошо, что болело, и почему индустрия искала что-то лучше.

---

## Слайд 3 — MPA

Итак, MPA — Multi-Page Application. Это самый первый и самый простой подход. Именно так строился весь веб в 2000-х.

---

## Слайд 3.1 — MPA — как это работает?

Посмотрите на схему. Всё предельно линейно: вы вводите URL в браузере, браузер отправляет запрос на сервер. Сервер определяет маршрут, идёт в базу данных или в какой-то API, получает данные, рендерит из этих данных готовый HTML и отдаёт его обратно браузеру. Браузер просто отображает готовую страницу.

Главный момент: каждый переход по ссылке — это новый HTTP-запрос и полная перезагрузка страницы. Весь экран мигает, всё грузится заново.

---

## Слайд 3.2 — MPA плюсы и минусы

Что хорошего в MPA? Архитектура предельно простая. Вся логика на сервере, серверный язык один — PHP, Python, Ruby, что угодно. SEO работает из коробки, потому что поисковый бот получает уже готовый HTML. Приложение работает даже без JavaScript. Первая загрузка быстрая.

Но вот где болело: при каждом действии пользователя — нажал кнопку, перешёл по ссылке, отправил форму — страница перезагружается полностью. Нельзя сделать плавный переход между страницами. Нельзя управлять фокусом после действия. Если пользователь часто взаимодействует с интерфейсом — получается ужасный UX, постоянно всё мигает.

---

## Слайд 3.3 — MPA примеры

Wikipedia работает именно так. Большинство сайтов на WordPress — тоже MPA. Классические интернет-магазины эпохи 2000-х.

И вот что хотелось: добавить интерактивности без полной перезагрузки страницы. Чтобы можно было обновить один блок на странице, не перегружая всё остальное.

---

## Слайд 4 — PEMPA

Именно это и придумали в рамках PEMPA — Progressively Enhanced Multi-Page Application. Прогрессивно улучшенное многостраничное приложение.

---

## Слайд 4.1 — PEMPA — идея

Идея простая: не выбрасываем MPA, а кладём поверх него JavaScript. Берём обычный MPA, и когда пользователь нажимает на ссылку или отправляет форму — JavaScript перехватывает это событие, делает запрос через fetch или XMLHttpRequest, получает данные и обновляет только нужную часть DOM. Без перезагрузки.

Ключевой принцип — progressive enhancement: приложение должно работать даже без JavaScript. JS — это улучшение, а не обязательное условие.

---

## Слайд 4.2 — PEMPA плюсы и минусы

Что решили: нет полной перезагрузки, есть плавные переходы, работает без JS.

Но появились новые проблемы, и серьёзные. Самая главная — дублирование логики рендеринга. Сервер генерирует HTML с помощью шаблонизатора — допустим, Jinja или PHP. Но когда приходит AJAX-ответ, нам нужно обновить DOM на клиенте. И мы пишем ту же самую логику снова, только на JavaScript. Список элементов рендерим и на сервере, и на клиенте.

Плюс появляются гонки запросов: пользователь быстро кликает, летит несколько запросов, ответы приходят в непредсказуемом порядке. Состояние разбросано по разным местам кода, нет центрального хранилища.

---

## Слайд 4.3 — Проблема дублирования

Вот она, проблема в коде. Слева — шаблон на сервере. Допустим, Jinja: цикл for по items, рисуем li для каждого. Справа — тот же самый список, но уже на клиенте через JavaScript: forEach, createElement, appendChild. Одна и та же логика, написанная дважды, на разных языках. При изменении структуры нужно менять в двух местах. Это кошмар для поддержки.

Хотелось: один код рендеринга, который работает везде.

---

## Слайд 5 — SPA

Именно эту проблему и решили в SPA — Single Page Application. Убираем серверный рендеринг полностью. Всё UI рисует клиент.

---

## Слайд 5.1 — SPA — решение

Схема: CDN отдаёт один пустой index.html. Браузер скачивает его и JavaScript-бандл. Дальше JavaScript берёт управление: рисует весь интерфейс, переключает страницы, управляет состоянием. Сервер остаётся только как REST API — он отдаёт голые данные, JSON. Никакого HTML от сервера больше нет.

---

## Слайд 5.2 — SPA плюсы и минусы

Что получили: нет дублирования — один язык, одна логика. Богатый интерактивный интерфейс. Фронтенд и бэкенд полностью независимы, можно развивать отдельно. После первой загрузки переходы мгновенные.

Но появились новые проблемы. Огромный JS-бандл — пользователь должен скачать и выполнить много кода до того, как увидит хоть что-нибудь. Водопад запросов — сейчас покажу. Тяжело на слабых устройствах: весь рендеринг на CPU пользователя. Сложное управление состоянием — это буквально 30-50% кода типичного SPA. И SEO-проблемы: поисковый бот приходит на страницу и видит пустой div.

---

## Слайд 5.3 — Водопад зависимостей

Вот как выглядит загрузка SPA в цифрах. Ноль миллисекунд: браузер получает пустой index.html. Нет ничего кроме пустого div. Через 200 миллисекунд загружается и выполняется app.js — роутер, все библиотеки. Ещё через 200 миллисекунд определяется текущий роут, начинает загружаться код конкретной страницы. Ещё 200 миллисекунд — компонент монтируется и только теперь делает fetch за данными. И только после ответа API пользователь наконец видит контент.

Это может быть секунда и больше на пустом экране. На медленном соединении — ещё хуже.

---

## Слайд 5.4 — Эволюция архитектур

Вот полная картина эволюции. MPA — просто, но нет интерактивности. PEMPA — интерактивность есть, но дублирование кода. SPA — мощно, но медленный старт и сложное состояние. И сейчас индустрия движется к SSR и React Server Components — это возврат к серверному рендерингу, но уже с умной гидратацией. Next.js делает именно это. Но это тема следующих лекций.

## Слайд 6 — React (заставка)

Ну что, перейдём наконец к самому React.

---

## Слайд 6.1 — Что такое React?

React — это JavaScript-библиотека для создания пользовательских интерфейсов. Не фреймворк — именно библиотека. Это важно: React отвечает только за UI-слой. За роутинг, работу с сервером, форму — это всё внешние решения.

Создан в Facebook в 2013 году. Open source под MIT лицензией — то есть можно использовать бесплатно в любых проектах. Используется в продакшне в Facebook, Instagram, Netflix, Airbnb, Twitter и тысячах других компаний.

---

## Слайд 6.2 — Ключевая идея

Главная идея React умещается в одну строку: UI = f(state). Интерфейс — это функция от состояния. Дайте React состояние, и он сам нарисует правильный интерфейс. Изменилось состояние — React сам определит, что поменялось в DOM, и обновит только нужные части.

Сравните два подхода. Слева — императивный: вы вручную находите элемент и меняете его содержимое. Вы сами говорите КАК менять DOM. Справа — декларативный React: вы описываете ЧТО должно быть на экране. Если count изменился — React сам разберётся, как обновить DOM. Вы не думаете о DOM вообще.

---

## Слайд 7 — Создание проекта

Как начать работу с React? Самый простой способ — create-react-app. Одна команда: npx create-react-app my-app, переходим в папку, npm start — и у вас уже работающее React-приложение с hot reload.

Справедливое замечание: сегодня в индустрии чаще используют Vite или Next.js — они быстрее и гибче. Но CRA проще для первого знакомства, поэтому начнём с него.

---

## Слайд 7.1 — Структура файлов CRA

Вот что вы увидите после создания проекта. Папка public — там только один HTML-файл. Папка src — весь ваш код. index.js — точка входа, именно отсюда React стартует. App.js — корневой компонент. CSS-файлы — стили.

Обратите внимание: node_modules уже может весить 200-300 мегабайт. Это нормально, не пугайтесь.

---

## Слайд 7.2 — public/index.html

Вот этот единственный HTML-файл. Посмотрите на него. В нём почти ничего нет. Только один div с id="root". Это та самая точка монтирования, о которой мы говорили в архитектуре SPA. React возьмёт этот div и вставит туда весь интерфейс приложения.

---

## Слайд 8 — index.js — точка входа

А вот index.js — точка входа. Здесь происходит связка React с реальным DOM. ReactDOM.createRoot принимает тот самый div#root и создаёт корень React-дерева. Потом root.render запускает рендеринг компонента App внутрь этого корня. Всё — с этого момента React управляет содержимым div#root.

---

## Слайд 9 — Какие бывают React-элементы?

Теперь важный концептуальный момент. React не работает напрямую с реальным DOM. Он работает с виртуальными описаниями — React-элементами. Это просто объекты JavaScript, которые описывают, что должно быть на экране.

Есть два вида React-элементов.

---

## Слайд 9.1 — React Element DOM

Первый вид: DOM-элемент. Когда вы пишете в JSX что-то с маленькой буквы — h1, div, span — React понимает, что это нативный HTML-тег, и создаёт соответствующий DOM-узел.

Посмотрите на код: JSX слева и что он компилируется справа. React.createElement принимает три аргумента: тип элемента, пропсы и дочерние элементы. Именно этот объект-описание React сравнивает при каждом рендере, чтобы понять, что изменилось.

Маленькая буква всегда означает DOM-элемент.

---

## Слайд 9.2 — React Element Component

Второй вид: компонент. Если вы пишете с большой буквы — Title, Button, StudentCard — React понимает, что это компонент. Он вызовет функцию этого компонента, получит JSX, и уже из JSX создаст DOM-элементы.

Большая буква — это обязательное соглашение. Если напишете компонент с маленькой буквы, React воспримет его как несуществующий HTML-тег и ничего хорошего не выйдет.

---

## Слайд 9.3 — Виртуальный DOM

React-элементы складываются в виртуальное DOM-дерево — лёгкое JS-представление реального DOM. Это просто объект в памяти, а не реальные браузерные узлы. Слева — виртуальное дерево: вложенные объекты с type, props, children. Справа — то, что в итоге оказывается в браузере.

---

## Слайд 9.4 — Как работает Virtual DOM

Процесс из трёх шагов. Первый — Рендер: React вызывает компоненты и строит новое виртуальное дерево. Второй — Diffing: сравнивает новое дерево со старым, находит минимальный набор изменений. Третий — Commit: применяет только реальные изменения в браузерный DOM.

Манипуляции с реальным DOM дороги — Virtual DOM позволяет делать их минимально.

---

## Слайд 10 — JSX

Теперь поговорим о JSX. JavaScript XML, или JavaScript Syntax eXtension. Это расширение синтаксиса JavaScript, которое позволяет писать HTML-подобную разметку прямо в JavaScript-файле.

---

## Слайд 10.1 — JSX правила

Вот важные правила JSX. Первое: один корневой элемент. Нельзя вернуть два элемента рядом без обёртки. Второе: комментарии пишутся в фигурных скобках. Третье: всё, что в фигурных скобках — это JavaScript-выражение. Можно вычислять, вызывать функции, всё что угодно. Четвёртое: class пишем как className — потому что class зарезервировано в JavaScript. Пятое: условный рендеринг через &&: если isActive — показываем span, если нет — не показываем ничего.

---

## Слайд 10.2 — JSX — все теги должны быть закрыты

В HTML некоторые теги можно не закрывать: img, input, br, hr. В JSX это недопустимо — все теги обязательно закрываются. Теги без содержимого закрываются самозакрывающим синтаксисом: />. То же самое касается компонентов — можно писать <StudentList /> или <StudentList></StudentList>.

---

## Слайд 10.3 — JSX → JS

И важно понимать, что JSX — это не магия. Это синтаксический сахар. Babel при сборке компилирует JSX в обычные вызовы React.createElement. То, что слева написано красиво и читаемо — справа превращается в вложенные вызовы функций. JSX просто делает этот код человекочитаемым. Именно поэтому раньше нужно было писать import React from 'react' в каждом файле — без него React.createElement был бы недоступен. В современных версиях это уже не нужно — трансформация автоматическая.

---

## Слайд 11 — App.js — корневой компонент

App.js — это обычно корневой компонент приложения. Он импортирует и скомпоновывает другие компоненты. Вот типичный App.js: рендерит Header с пропсом title и StudentList. Обратите внимание на export default — это обязательно, чтобы другие файлы могли импортировать компонент.

---

## Слайд 12 — Компоненты

Переходим к компонентам — главному строительному блоку React-приложения. Весь ваш интерфейс — это дерево компонентов. Каждый компонент отвечает за свой кусок UI, независим и переиспользуем.

---

## Слайд 12.1 — Props — аргументы компонента

Props (properties) — способ передать данные от родителя к дочернему компоненту. Передаём их как атрибуты JSX, принимаем как аргумент функции — удобно сразу деструктурировать. Три важных момента: пропсы только для чтения — компонент не должен их изменять; данные текут сверху вниз; передавать можно что угодно — строки, числа, функции, другие компоненты.

---

## Слайд 12.2 — Классовый компонент

Исторически первым типом компонентов были классовые. Вы наследуете от React.Component, обязательно реализуете метод render, который возвращает JSX. Props доступны через this.props, состояние через this.state и this.setState.

Такой код вы можете встретить в старых проектах, поэтому нужно его понимать и уметь читать.

---

## Слайд 12.3 — Функциональный компонент

Но сейчас пишут иначе. Функциональный компонент — это просто функция. Принимает пропсы как аргумент — удобно сразу деструктурировать — и возвращает JSX. Можно написать через function или через стрелочную функцию. Компонент возвращает ReactElement или null.

---

## Слайд 12.4 — Классовый VS Функциональный

Почему функциональные лучше? Смотрите сравнение. Классовые: много бойлерплейта, сложнее читать, методы жизненного цикла — componentDidMount, componentDidUpdate — которые сложно комбинировать, постоянные проблемы с this и привязкой контекста. Устаревший стиль.

Функциональные: лаконичный код, легче читать и тестировать, нет проблем с this, и главное — хуки, которые заменяют весь жизненный цикл намного элегантнее. Всегда используйте функциональные компоненты в новом коде.

---

## Слайд 12.5 — Создание компонентов

Как организовать файлы? Компоненты обычно выносят в папку components. Каждый компонент — отдельный файл. Расширение .jsx или .js — разницы нет, договоритесь в команде.

Вот StudentItem: принимает name и grade через пропсы, рендерит два span. Компонент ничего не знает о том, откуда берутся эти данные — он просто отображает то, что ему передали. Это и делает компоненты переиспользуемыми.

---

## Слайд 13 — Стили и классы в React

Поговорим про стили.

---

## Слайд 13.1 — className вместо class

Первое и самое частое: в JSX атрибут называется className, а не class. Если напишете class — React выдаст предупреждение, и в некоторых браузерах могут быть проблемы. Причина: class — зарезервированное ключевое слово в JavaScript, поэтому в JSX используется другое имя.

---

## Слайд 13.2 — Способы задавать стили

Три способа. Первый — обычный CSS-файл: импортируете его в компонент, используете className. Привычно и понятно. Второй — inline-стили: передаёте объект через двойные фигурные скобки. Важно: свойства в camelCase — fontSize, не font-size. Третий — динамические классы: вычисляете строку с классами на основе состояния. Очень часто нужно в реальных проектах.

---

## Слайд 13.3 — CSS Modules

И четвёртый подход, который рекомендую — CSS Modules. Файл называется Component.module.css, импортируете как объект styles. Имена классов доступны как свойства этого объекта. Главное преимущество: CSS Modules автоматически делают классы уникальными — добавляют хэш к имени. Никаких конфликтов имён между компонентами, даже если вы называете классы одинаково.

---

## Слайд 14 — Отрисовка массива

Теперь очень частая задача: как отрендерить список элементов?

---

## Слайд 14.1 — Метод .map()

React умеет рендерить массив JSX-элементов. Поэтому стандартный паттерн — это .map(). У нас есть массив students, мы вызываем map, для каждого студента возвращаем компонент StudentItem с нужными пропсами. Обратите внимание на пропс key — к нему вернёмся.

---

## Слайд 14.2 — Зачем нужен key?

key — это специальный пропс, который помогает React эффективно обновлять список. Когда список изменяется — элементы добавляются, удаляются, переставляются — React использует key, чтобы понять, какой элемент соответствует какому DOM-узлу.

Три правила. Первое: никогда не используйте индекс массива как key. Если порядок элементов меняется — React запутается и будет делать неправильные обновления. Второе: не генерируйте key на лету через Math.random() — каждый рендер будет создавать новый ключ, React будет думать, что все элементы заменились, и перемонтирует весь список. Третье: используйте стабильный уникальный идентификатор — обычно это id из базы данных.

---

## Слайд 15 — Хуки (заставка)

Переходим к хукам. Это одна из самых важных концепций в современном React.

---

## Слайд 15.1 — Что такое хуки?

Хуки — это специальные функции, которые позволяют функциональным компонентам работать с состоянием и жизненным циклом. До хуков это было доступно только в классовых компонентах. В 2019 году React 16.8 добавил хуки, и это изменило всё.

Четыре правила: работают только в функциональных компонентах, имена начинаются с use, нельзя вызывать внутри условий и циклов, и — это вытекает из предыдущего — всегда вызываются в одном и том же порядке при каждом рендере. React использует порядок вызовов хуков для их идентификации, поэтому любые изменения порядка ломают всё.

---

## Слайд 15.2 — useState

Первый и самый главный хук — useState. Добавляет переменную состояния к компоненту.

Синтаксис: деструктурируем массив на два элемента. Первый — текущее значение состояния, второй — функция для его изменения. В аргументе useState передаём начальное значение.

Посмотрите на Counter: count начинается с нуля. При клике на кнопку вызывается setCount с новым значением. React видит, что состояние изменилось, запускает перерендер компонента, и на экране появляется новое значение. Вы не трогаете DOM — React делает всё сам.

---

## Слайд 15.3 — useEffect

Второй важный хук — useEffect. Он позволяет выполнять побочные эффекты: запросы к API, подписки на события, работу с таймерами, прямые манипуляции с DOM.

Вот пример: при монтировании компонента делаем fetch к API, получаем данные, записываем в состояние через setStudents. Пустой массив в качестве второго аргумента означает: запустить эффект один раз при монтировании.

---

## Слайд 15.4 — useEffect — зависимости

Второй аргумент useEffect — это массив зависимостей. Он управляет тем, когда эффект перезапускается.

Нет второго аргумента — эффект запускается после каждого рендера. Пустой массив — только при монтировании. Массив с переменными — при изменении любой из них. И важный паттерн — возвращаемая функция очистки: она вызывается перед следующим запуском эффекта и при размонтировании. Используется для очистки таймеров, отписки от событий, закрытия соединений.

---

## Слайд 15.5 — useRef

useRef — хук для двух вещей. Первое: ссылка на DOM-элемент. Создаёте ref, передаёте его как атрибут ref на элемент, и потом через ref.current обращаетесь к нативному DOM-узлу. В примере — фокусируем input.

Второе применение useRef — хранение значения, которое должно сохраняться между рендерами, но изменение которого не должно вызывать перерендер. В отличие от useState, изменение ref.current не вызывает ре-рендер.

---

## Слайд 15.6 — useCallback и useMemo

Два хука для оптимизации производительности.

useCallback кэширует функцию. Без него при каждом рендере компонента создаётся новый объект функции. Если эту функцию передавать как проп дочернему компоненту — дочерний будет перерендериваться каждый раз, думая что проп изменился.

useMemo кэширует результат вычисления. Если у вас есть тяжёлая операция — например, reduce по большому массиву — useMemo пересчитает результат только когда изменится массив items, а не при каждом рендере.

На ранних этапах не злоупотребляйте этими хуками — они усложняют код. Применяйте, когда есть реальная проблема с производительностью.

---

## Слайд 16 — Кастомные хуки

Одна из самых мощных возможностей хуков — возможность создавать свои. Кастомный хук — это просто функция, которая начинается с use и внутри использует другие хуки.

Зачем? Чтобы переиспользовать логику. Если у вас в трёх компонентах одинаковый код загрузки данных — вынесите его в кастомный хук.

---

## Слайд 16.1 — Пример: useFetch

Вот классический пример: useFetch. Хук принимает url, внутри хранит три состояния: данные, флаг загрузки и ошибку. useEffect при изменении url делает fetch и обновляет состояния. Возвращает объект с тремя значениями.

---

## Слайд 16.2 — Использование useFetch

А вот как это используется. Компонент StudentList вызывает useFetch, деструктурирует результат. Пока идёт загрузка — показывает "Загрузка...". Если ошибка — показывает "Ошибка!". Если всё хорошо — рендерит список. Весь код загрузки спрятан в хуке, компонент чистый.

---

## Слайд 17 — Fragment

И последняя тема — Fragment.

---

## Слайд 17.1 — Проблема

React требует, чтобы компонент возвращал один корневой элемент. Нельзя вернуть два соседних элемента — это синтаксическая ошибка.

Первое желание — обернуть в div. Но div создаёт лишний DOM-узел. Иногда это ломает CSS — например, если вы используете flexbox или grid и лишний div нарушает структуру. Иногда это семантически неправильно.

---

## Слайд 17.2 — Решение: Fragment

Fragment — это специальный компонент-обёртка, который не создаёт DOM-узла. Длинная форма: импортируем Fragment из react, используем как обычный тег. Короткая форма — просто пустые теги <> и </>. Именно её вы будете видеть и писать чаще всего.

---

## Слайд 17.3 — Fragment с key

Если нужно рендерить список фрагментов — например, каждый элемент списка состоит из нескольких соседних тегов — нужно использовать длинную форму с ключом. Короткий синтаксис <> не поддерживает атрибуты.

---

## Слайд 18 — TypeScript в React (заставка)

Переходим к TypeScript.

---

## Слайд 18.1 — Зачем TypeScript?

TypeScript добавляет статическую типизацию в JavaScript. Четыре причины использовать его в React-проектах: IDE подсказывает props и их типы автоматически; ошибки находятся на этапе компиляции, не в браузере; код проще читать и рефакторить; это стандарт де-факто в коммерческих React-проектах.

Создать проект с TypeScript: npm create vite@latest my-app -- --template react-ts.

---

## Слайд 18.2 — Типизация компонента — вариант 1

Первый вариант: описываем тип пропсов отдельно через type, стрелочная функция с типизированными props. Вопросительный знак — необязательный проп. Можно сразу задать значение по умолчанию прямо в деструктуризации.

---

## Слайд 18.3 — Типизация компонента — вариант 2

Второй вариант: FC<Props> — специальный тип из React для функционального компонента. Явно указывает, что функция — React-компонент. Минус: запрещает возвращать undefined, только JSX или null.

---

## Слайд 18.4 — Типизация useState

При работе с useState TypeScript часто выводит тип автоматически. Но для сложных типов — массивов, объектов, union-типов — нужно указывать явно через дженерик: useState<Student[]>([]). Для примитивов вроде boolean TypeScript выводит тип сам.

---

## Слайд 18.5 — Типизация событий

Обработчики событий тоже нужно типизировать. ChangeEvent<HTMLInputElement> — для обработчика onChange у input. FormEvent<HTMLFormElement> — для onSubmit у form. Импортируем эти типы прямо из react.
