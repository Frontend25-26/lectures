Зачем нужен сборщик

Жизнь без сборщика

<!-- index.html - порядок тегов важен, иначе «ReferenceError» -->
<script src="vendor/jquery.js"></script>
<script src="vendor/lodash.js"></script>
<script src="utils/helpers.js"></script>
<script src="components/modal.js"></script>
<script src="components/cart.js"></script>
<script src="app.js"></script>
  • Все переменные в глобальном скоупе - легко получить конфликт имён
  • Браузер делает отдельный HTTP-запрос на каждый файл
  • TypeScript, SCSS, JSX - браузер не понимает нативно
  • В продакшн уходит читаемый исходный код без оптимизации

Что хотим от сборки

Модули
->
import/export без конфликтов, явные зависимости между файлами
Трансформации
->
TypeScript -> JS, SCSS -> CSS, JSX -> JS, новый синтаксис -> старый
Оптимизация
->
Минификация, удаление неиспользуемого кода, разбиение на чанки
Dev experience
->
Hot Module Replacement, source maps, быстрый перезапуск

Два класса инструментов

Task Runner vs Bundler

Task Runner - Gulp

  • Императивный - описываешь как делать
  • Не знает ничего про import/export
  • Любая задача с файлами - без ограничений

Bundler - Webpack, Vite

  • Декларативный - описываешь что хочешь получить
  • Понимает граф зависимостей
  • Tree shaking, code splitting из коробки

Webpack начинает с entry point, обходит все import рекурсивно и строит граф зависимостей

Минимальный webpack.config.js

// webpack.config.js
module.exports = {
    entry: './src/index.js',       // с чего начинать обход

    output: {
        filename: 'bundle.js',
        path: path.resolve(__dirname, 'dist'),
    },

    mode: 'development',           // 'production' - минификация + оптимизации
};
  • entry - точка входа, с которой начинается граф
  • output - куда положить результат
  • mode - переключает пресеты оптимизаций

Loaders - трансформация файлов

По умолчанию Webpack понимает только JS и JSON. Loader учит его обрабатывать всё остальное

Loader Что делает
babel-loader ES2020+ -> ES5, JSX -> JS
ts-loader TypeScript -> JS
css-loader Понимает @import и url() в CSS
sass-loader SCSS -> CSS
file-loader Копирует файл в output, возвращает URL

Plugins - постобработка бандла

Loaders трансформируют отдельные файлы. Plugins работают с результатом сборки целиком 

const HtmlWebpackPlugin = require('html-webpack-plugin');
const MiniCssExtractPlugin = require('mini-css-extract-plugin');

module.exports = {
    plugins: [
        // Генерирует index.html и автоматически вставляет тег <script>
        new HtmlWebpackPlugin({ template: './src/index.html' }),

        // Выносит CSS в отдельный файл вместо inline <style>
        new MiniCssExtractPlugin({ filename: 'styles.css' }),
    ],
};

Code Splitting

Разбивает бандл на части - браузер загружает только то, что нужно прямо сейчас 

// Статический импорт - попадает в основной бандл
import { format } from 'date-fns';

// Динамический импорт - Webpack создаёт отдельный чанк
// Загружается только когда пользователь открывает страницу настроек
const SettingsPage = React.lazy(() => import('./pages/Settings'));

Tree Shaking

Убирает неиспользуемый код из бандла. Работает только со статическими import/export 

// utils.js - экспортирует три функции
export const add = (a, b) => a + b;
export const subtract = (a, b) => a - b;
export const multiply = (a, b) => a * b;

// app.js - импортирует только одну
import { add } from './utils';

В production-бандл попадёт только add - subtract и multiply будут удалены

  • Включён автоматически при mode: 'production'
  • Не работает с CommonJS (require()) - только ESM

Webpack в Next.js

Что Next.js настраивает за вас

Next.js скрывает webpack.config.js - вы работаете с фреймворком, а не с Webpack напрямую

TypeScript
->
Автоматически через ts-loader / babel-loader - просто создайте tsconfig.json
CSS Modules
->
Файл *.module.css - и стили автоматически изолируются по компоненту
Code Splitting
->
Каждая страница в app/ автоматически становится отдельным чанком
HMR
->
Fast Refresh - изменения в компоненте применяются без перезагрузки страницы

Кастомизация через next.config.js

Если стандартных возможностей не хватает - можно расширить конфиг Webpack 

// next.config.js
module.exports = {
    webpack(config, { isServer }) {
        // Добавляем SVG-лоадер
        config.module.rules.push({
            test: /\.svg$/,
            use: ['@svgr/webpack'],
        });

        // Добавляем плагин только для клиентской сборки
        if (!isServer) {
            config.plugins.push(new MyAnalyticsPlugin());
        }

        return config;  // обязательно вернуть изменённый конфиг
    },
};

Turbopack - будущее Next.js

В Next.js 15 появился Turbopack - написанный на Rust замена Webpack для dev-режима

Webpack (текущий)

  • Зрелый, огромная экосистема
  • Все edge-кейсы покрыты
  • Медленный холодный старт на больших проектах
  • HMR замедляется с ростом приложения

Turbopack (новый)

  • До 10x быстрее холодный старт
  • HMR не деградирует с размером проекта
  • Только dev-режим (production - всё ещё Webpack)
  • Не все webpack-плагины совместимы
// package.json - включить Turbopack для next dev
"scripts": {
    "dev": "next dev --turbopack"
}
