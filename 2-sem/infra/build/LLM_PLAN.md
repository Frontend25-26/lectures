# Лекция: Сборка
# Длительность: ~90 минут (15 мин введение + 5 × 12–15 мин)

---

## Введение (лектор) — Зачем нужна сборка?

### Что говорить (15 минут)

**Вводный вопрос к аудитории:**
Поднимите руку, кто писал HTML, CSS и JS без каких-либо инструментов — просто открывал файл в браузере? Вот это и есть «жизнь без сборки». Сегодня поговорим о том, почему так уже никто не работает.

---

**Проблема 1: Много файлов — много запросов**

Представьте: у вас 30 JS-файлов. Браузер делает 30 HTTP-запросов. Каждый запрос — это задержка. На медленном соединении страница грузится 5 секунд. Решение — объединить всё в один файл-бандл.

---

**Проблема 2: Браузеры не понимают современный JS**

Вы пишете `import` / `export`, стрелочные функции, `async/await`. Старые браузеры этого не знают. Нужен инструмент, который переведёт ваш код на «старый» JavaScript. Это называется транспиляция.

---

**Проблема 3: Код нужно оптимизировать перед продакшном**

- Пробелы, комментарии, длинные имена переменных — занимают место → **минификация**
- Мёртвый код, который никто не вызывает — тоже занимает место → **tree shaking**
- Картинки, шрифты, CSS — всё это тоже нужно обработать

---

**Проблема 4: Удобство разработки**

- Горячая перезагрузка: сохранил файл — браузер обновился
- Source maps: ошибка в `bundle.min.js:1:48291` → видишь нужную строку в исходнике
- Локальный сервер с HTTPS, проксированием API

---

**Итого: что делает инструмент сборки?**

```
Исходники (JS, TS, JSX, CSS, изображения)
           ↓
  Трансформации (Babel, PostCSS, TypeScript)
           ↓
  Оптимизации (minify, tree shake, hash)
           ↓
    dist/ (готовые файлы для браузера)
```

Инструмент сборки — это конвейер. Сырой код заходит с одного конца, готовые файлы выходят с другого.

---

**Два разных подхода к сборке**

Исторически сложилось два способа организовать этот конвейер:

- **Task runner** (Gulp, Grunt) — вы описываете задачи: «возьми эти файлы, прогони через минификатор, положи сюда». Явный порядок, ручное управление.
- **Бандлер** (Webpack, Rollup, esbuild, Vite) — вы указываете точку входа, бандлер сам строит граф зависимостей и понимает, что нужно обработать.

Сегодня студенты расскажут о каждом подходе и конкретных инструментах.

## Студент 1 — Webpack

### Тема: Webpack — бандлер с графом зависимостей (12–15 минут)

**1. Что такое Webpack (2 мин)**

Webpack появился в 2012 году и долго был стандартом индустрии. До сих пор лежит под капотом create-react-app и многих корпоративных проектов.

Главная идея: Webpack строит **граф зависимостей**. Начинает с точки входа (`entry`), обходит все `import` и `require` в коде, находит все файлы, которые нужны приложению, и собирает их в бандл. Вам не нужно вручную указывать список файлов — Webpack сам разберётся.

**2. Ключевые концепции (5 мин)**

- **entry** — точка входа, с которой начинается граф: `./src/index.js`
- **output** — куда и под каким именем сохранить результат
- **loaders** — трансформируют файлы перед включением в граф. CSS-файл сам по себе Webpack не понимает — нужен `css-loader`. JSX — нужен `babel-loader`. Каждый loader решает одну задачу
- **plugins** — расширяют возможности: создать HTML-файл (`HtmlWebpackPlugin`), вынести CSS в отдельный файл (`MiniCssExtractPlugin`)
- **mode** — `development` (читаемый код, source maps) vs `production` (минификация, tree shaking)

```js
// webpack.config.js
module.exports = {
  entry: './src/index.js',
  output: {
    filename: 'bundle.[contenthash].js',
    path: path.resolve(__dirname, 'dist'),
  },
  mode: 'production',
  module: {
    rules: [
      { test: /\.jsx?$/, use: 'babel-loader', exclude: /node_modules/ },
      { test: /\.css$/, use: ['style-loader', 'css-loader'] },
    ],
  },
  plugins: [new HtmlWebpackPlugin({ template: './public/index.html' })],
};
```

**3. Dev-сервер (2 мин)**

`webpack-dev-server` — запускает локальный сервер с HMR (Hot Module Replacement). Изменяешь файл — в браузере обновляется только изменённый модуль, без полной перезагрузки страницы.

**4. Плюсы и минусы (2 мин)**

Плюсы: огромная экосистема плагинов, гибкость настройки под любой нестандартный проект, HMR из коробки.

Минусы:
- Конфиг может разрастись до 200+ строк
- Холодный старт на большом проекте — 30–60 секунд
- Порог вхождения высокий

**5. Итог (1 мин)**

Webpack — мощный и гибкий. Хорошо подходит для сложных корпоративных проектов с нестандартными требованиями. Всё ещё живёт во многих продакшн-проектах.

## Студент 2 — Gulp

### Тема: Gulp — task runner, или «сборка руками» (12–15 минут)

**1. Что такое task runner и зачем он нужен (2 мин)**

Gulp — это не бандлер. Это **task runner**: инструмент для автоматизации повторяющихся задач. Вместо того чтобы строить граф зависимостей, вы явно описываете задачи: «возьми эти файлы, прогони через минификатор, положи вот сюда».

Появился в 2013 году как альтернатива Grunt с более удобным API. Активно использовался в 2014–2018 годах, сегодня встречается в легаси-проектах и там, где нужен явный контроль над конвейером.

**2. Ключевые концепции (4 мин)**

Gulp работает с **потоками** (streams): файлы читаются, проходят через цепочку плагинов и записываются на диск.

- `gulp.src()` — берёт файлы по glob-паттерну
- `.pipe()` — передаёт в следующий плагин
- `gulp.dest()` — записывает результат

```js
// gulpfile.js
const { src, dest, watch, series, parallel } = require('gulp')
const sass = require('gulp-sass')(require('sass'))
const cleanCSS = require('gulp-clean-css')
const uglify = require('gulp-uglify')
const concat = require('gulp-concat')

function styles() {
  return src('src/styles/**/*.scss')
    .pipe(sass())           // SCSS → CSS
    .pipe(cleanCSS())       // минификация
    .pipe(dest('dist/css')) // сохранить
}

function scripts() {
  return src('src/js/**/*.js')
    .pipe(concat('bundle.js')) // объединить в один файл
    .pipe(uglify())            // минификация
    .pipe(dest('dist/js'))
}

function watchFiles() {
  watch('src/styles/**/*.scss', styles)
  watch('src/js/**/*.js', scripts)
}

exports.build = parallel(styles, scripts)
exports.default = series(parallel(styles, scripts), watchFiles)
```

**3. Задачи и их порядок (3 мин)**

Gulp позволяет явно управлять порядком выполнения:

- `series(a, b)` — задачи выполняются последовательно: сначала `a`, потом `b`
- `parallel(a, b)` — задачи выполняются параллельно

Это удобно для сложных пайплайнов: сначала очистить `dist/`, потом параллельно собрать CSS и JS, потом скопировать картинки.

**4. Типичный набор задач в реальном проекте (2 мин)**

- Компиляция Sass/Less → CSS
- Конкатенация и минификация JS
- Оптимизация изображений
- Копирование статики
- Генерация source maps
- Инвалидация кэша (добавление хэша к именам файлов)

**5. Плюсы и минусы (2 мин)**

Плюсы: явный и предсказуемый порядок задач; легко добавить любую обработку файлов; не привязан к JS-модулям — работает с любыми файлами.

Минусы: нет графа зависимостей — вы сами управляете, какие файлы обрабатывать; нет tree shaking; в современных SPA-проектах уступает бандлерам по возможностям.

**6. Итог (1 мин)**

Gulp отлично подходит для задач автоматизации: обработка ассетов, скрипты деплоя, генерация документации. Для сборки SPA его сегодня почти не используют, но в легаси-проектах и нестандартных пайплайнах он по-прежнему актуален.

## Студент 3 — Rollup и esbuild

### Тема: Специализированные бандлеры (12–15 минут)

**1. Rollup — бандлер для библиотек (6 мин)**

Rollup создавался не для сборки приложений, а для публикации кода в npm. Именно поэтому он делает **tree shaking** лучше всех остальных — буквально выкидывает весь неиспользуемый код на уровне отдельных экспортов.

Если вы делаете `import { add } from 'math-lib'`, Rollup включит в бандл только функцию `add`, полностью выкинув остальное из библиотеки.

Главная фишка: поддержка нескольких форматов вывода одновременно.

```js
// rollup.config.js
export default {
  input: 'src/index.js',
  output: [
    { file: 'dist/lib.esm.js', format: 'esm' },          // для современных браузеров
    { file: 'dist/lib.cjs.js', format: 'cjs' },          // для Node.js / require()
    { file: 'dist/lib.umd.js', format: 'umd', name: 'MyLib' }, // универсальный
  ],
}
```

Один исходник — три разных формата на выходе. Именно так публикуют большинство npm-пакетов.

Важно знать: Rollup используется внутри Vite для продакшн-сборки. То есть когда вы запускаете `vite build` — под капотом работает Rollup.

**2. esbuild — экстремальная скорость (5 мин)**

esbuild появился в 2020 году. Написан на Go — это даёт параллельную обработку без накладных расходов JavaScript-рантайма.

Что умеет без дополнительных плагинов:
- Бандлинг JS/TS
- Трансформация TypeScript и JSX
- Минификация
- Tree shaking

```bash
# Собрать, трансформировать TypeScript и минифицировать — одна команда
esbuild src/index.ts --bundle --minify --outfile=dist/bundle.js
```

Скорость: то, что Webpack делает за 30 секунд, esbuild делает за 0.3 секунды. В 100 раз быстрее — не преувеличение.

Ограничения: нет HMR, нет CSS Modules, плагинная система гораздо беднее Webpack. Поэтому esbuild редко используют напрямую для сборки приложений — он живёт внутри других инструментов. Vite использует esbuild для трансформации файлов в dev-режиме.

**3. Итоговая таблица (2 мин)**

| Задача | Инструмент |
|--------|-----------|
| Приложение (легаси, сложный конфиг) | Webpack |
| npm-библиотека, UI kit | Rollup |
| Быстрая трансформация, CI-скрипты | esbuild |
| Автоматизация задач | Gulp |
| Новое приложение / SPA | Vite (следующий студент) |

## Студент 4 — Vite

### Тема: Vite — современный стандарт (12–15 минут)

**1. Проблема, которую решает Vite (2 мин)**

На большом проекте Webpack делает холодный старт 30–60 секунд. Нажал сохранить — ждёшь 2–3 секунды, пока обновится браузер. Умножьте это на сотню правок в день — это огромные потери времени разработчика.

**2. Идея Vite (4 мин)**

Vite (от французского «быстро») — инструмент от создателя Vue, Эвана Ю, вышел в 2020 году.

В **dev-режиме** Vite не делает бандлинг совсем. Современные браузеры умеют выполнять `import` нативно. Vite просто запускает сервер и отдаёт файлы по запросу, трансформируя их на лету через esbuild:

```
Браузер запрашивает App.jsx
    → Vite трансформирует JSX → JS за ~2 мс
    → Отдаёт файл браузеру
    → Браузер сам делает следующие import-запросы
```

Нет бандлинга → нет ожидания → мгновенный старт.

В **продакшне** Vite запускает Rollup и собирает оптимизированный бандл с tree shaking, минификацией и хэшами в именах файлов.

**3. Сравнение скорости (2 мин)**

| | Webpack | Vite |
|---|---|---|
| Холодный старт | ~30–60 с | ~200–500 мс |
| HMR | ~1–3 с | ~20–50 мс |

Разница — в 10–100 раз. В основе dev-скорости — esbuild (написан на Go, работает параллельно).

**4. Конфиг и проект (4 мин)**

```js
// vite.config.js — минималистичный конфиг
import { defineConfig } from 'vite'
import react from '@vitejs/plugin-react'

export default defineConfig({
  plugins: [react()],
})
```

Из коробки, без настройки: TypeScript, JSX, CSS Modules, Sass, статические ассеты, `.env`-файлы, HMR, source maps.

Переменные окружения: `import.meta.env.VITE_API_URL` — только переменные с префиксом `VITE_` попадают в браузерный код.

Создать проект:
```bash
npm create vite@latest my-app -- --template react-ts
cd my-app && npm install && npm run dev
```

**5. Итог (1 мин)**

Vite объединил лучшее: скорость esbuild в разработке, качество сборки Rollup в продакшне, простой конфиг. Сегодня это выбор по умолчанию для новых React, Vue, Svelte и других SPA-проектов.

## Студент 5 — Транспиляция: JS, TS и CSS

### Тема: Как код превращается в совместимый (12–15 минут)

**1. Что такое транспиляция (2 мин)**

Транспиляция — это преобразование кода из одного синтаксиса в другой на том же уровне абстракции. В отличие от компиляции (код → машинные инструкции), транспиляция — это JS → другой JS (или TS → JS, JSX → JS, SCSS → CSS).

Зачем: браузеры обновляются с разной скоростью, а языки развиваются быстро. Вы пишете на современном синтаксисе — транспилятор превращает это в код, понятный целевым браузерам.

```
Ваш код (ES2022+, TS, JSX, SCSS)  →  транспилятор  →  что понимает браузер
```

**2. Как работает транспилятор JS/TS (2 мин)**

Любой JS-транспилятор проходит три шага:

1. **Parse** — код разбирается в AST (Abstract Syntax Tree): дерево, где каждый узел — элемент кода (переменная, функция, выражение).
2. **Transform** — плагины обходят дерево и изменяют узлы: заменяют `const` на `var`, стрелочные функции на обычные, убирают типы TypeScript.
3. **Generate** — изменённое дерево превращается обратно в строку кода.

```js
// Исходный код
const greet = (name: string) => `Hello, ${name}!`

// После транспиляции (target: ES5)
var greet = function(name) {
  return 'Hello, ' + name + '!'
}
```

**3. Транспиляция JavaScript — Babel и альтернативы (4 мин)**

**Babel** — самый распространённый транспилятор JS. Написан на JavaScript, работает через плагины и пресеты.

```json
// .babelrc
{
  "presets": [
    ["@babel/preset-env", { "targets": "> 0.5%, not dead" }],
    "@babel/preset-react",
    "@babel/preset-typescript"
  ]
}
```

`@babel/preset-env` + `browserslist` — ключевая фишка: описываете целевую аудиторию браузеров, Babel сам решает, что трансформировать. Babel живёт внутри Webpack (`babel-loader`), Jest (`babel-jest`), CRA. Сильная сторона — кастомные плагины (styled-components, автоматический `displayName`). Слабая — скорость.

Быстрые альтернативы, написанные на системных языках:

- **esbuild** (Go) — встроен в Vite для dev-режима, в ~100 раз быстрее Babel, трансформирует TypeScript и JSX, но кастомные плагины не поддерживает
- **SWC** (Rust) — используется в Next.js 12+, в ~70 раз быстрее, поддерживает большинство Babel-плагинов

| | Babel | esbuild | SWC |
|---|---|---|---|
| Язык | JavaScript | Go | Rust |
| Скорость | базовая | ~100× | ~70× |
| Кастомные плагины | легко | сложно | частично |
| Где используется | Webpack, Jest, CRA | Vite (dev) | Next.js 12+ |

**4. Транспиляция TypeScript — tsc (2 мин)**

TypeScript имеет свой компилятор `tsc`. Он делает две вещи: проверяет типы и транспилирует код под нужный target.

```json
// tsconfig.json
{
  "compilerOptions": {
    "target": "ES2017",
    "strict": true,
    "noEmit": false
  }
}
```

Важное отличие от Babel/esbuild: `tsc` **проверяет типы**. Babel и esbuild просто стирают типы, не проверяя их. Поэтому в проектах часто разделяют задачи:
- `tsc --noEmit` — только проверка типов (в CI или pre-commit)
- esbuild или SWC — быстрая транспиляция для сборки

**5. Транспиляция CSS — PostCSS, Sass, Less (3 мин)**

CSS тоже транспилируют. Здесь два направления: препроцессоры и постпроцессоры.

**Препроцессоры** — расширяют синтаксис CSS, добавляя переменные, вложенность, миксины:

- **Sass/SCSS** — самый популярный. Компилируется через `sass` (Dart Sass). Поддерживает переменные (`$color`), вложенность, `@mixin`/`@include`, `@extend`.
- **Less** — аналог Sass, используется реже, встречается в легаси-проектах (в том числе Bootstrap 3 был на Less).

```scss
// SCSS
$primary: #3498db;

.button {
  background: $primary;

  &:hover {
    background: darken($primary, 10%);
  }

  &--large {
    padding: 16px 32px;
  }
}
```

```css
/* Скомпилированный CSS */
.button { background: #3498db; }
.button:hover { background: #217dbb; }
.button--large { padding: 16px 32px; }
```

**PostCSS** — постпроцессор: работает с обычным CSS через плагины. Не добавляет новый синтаксис сам по себе, но плагины могут всё что угодно:

- **Autoprefixer** — автоматически добавляет `-webkit-`, `-moz-` и другие вендорные префиксы на основе `browserslist`
- **cssnano** — минификация CSS
- **postcss-nested** — поддержка вложенности как в Sass, но в обычном CSS
- **postcss-custom-media** — `@custom-media` из черновика CSS

```css
/* Исходный CSS */
.box {
  display: flex;
  user-select: none;
}

/* После Autoprefixer */
.box {
  display: -webkit-box;
  display: -ms-flexbox;
  display: flex;
  -webkit-user-select: none;
  -moz-user-select: none;
  user-select: none;
}
```

PostCSS встроен в Vite и CRA, Autoprefixer часто настраивают через `browserslist` в `package.json`.

**6. Итог (1 мин)**

Транспиляция — невидимый слой между вашим кодом и браузером. JS: Babel (гибкость) или esbuild/SWC (скорость). TS: tsc для типов, esbuild/SWC для сборки. CSS: Sass/Less для расширенного синтаксиса, PostCSS (Autoprefixer) для совместимости и оптимизации.
