HTTP/HTTPS

HTTP (HyperText Transfer Protocol) - «протокол передачи гипертекста» (то есть документов, которые могут содержать ссылки, позволяющие организовать переход к другим документам)

Любой HTTP запрос преодолевает длинный путь через множество промежуточных узлов

Как может выглядеть путь:

  • сеть вуза
  • сеть интернет-провайдера
  • различные промежуточные сети
  • запрашиваемый ресурс

HTTP передаёт информацию между браузером и сервером в чистом тексте, позволяя видеть эту информацию в сети, через которую она проходит

HTTPS (HyperText Transfer Protocol Secure)

Протокол HTTPS используетcя поверх протокола TLS (Transport Layer Security)

TLS гибридная криптографическая система (использует несколько криптографических подходов - асимметрическое шифрование и симметричное шифрование)

Ассиметрическое шифрование используется для получения секретного ключа (один на сессию), а дальше все запросы шифруются и дешифруются с помощью этого секретного ключа

Решили ли мы вопрос с безопаностью?

Нет т.к. установка зашифрованного канала общения не говорит о том, с кем установлен канал общения

Сертификаты

В самом грубом приближении, цифровой сертификат – это файл, использующий электроннуй-цифровую подпись.

Цифровая подпись на сертификате означает, что некто удостоверяет тот факт, что данный открытый ключ принадлежит определенному лицу или организации.

Сертификаты связывают доменные имена с определенным публичным ключом

Чтобы сертификату доверял любой веб-браузер, он должен быть подписан аккредитованным удостоверяющим центром (центром сертификации, Certificate Authority, CA)

Как установить сертификат на свой сайт?

Шаг 1. Покупаем домен

Шаг 2. Получаем сертификат с помощью некоммерческого центра сертификации letsencrypt

(бесплатно на 90 дней с бесконечной возможностью продления)

Same-origin policy (SOP)

Политика "одинакового источника" ограничивает доступ окон и фреймов друг к другу

Политика "одинакового источника"

Источники одинаковые если у них одинаковые 3 параметра

  • протокол

Cross-Origin Resource Sharing (CORS)

  • No ‘Access-Control-Allow-Origin’ header is present on the requested resource.
  • Cross-Origin Request Blocked: The Same Origin Policy disallows reading the remote resource at https://example.com/
  • Access to fetch at ‘https://example.com’ from origin ‘http://localhost:3000’ has been blocked by CORS policy.

Представим ситуацию

С сайта team10.ya-itmo.ru нужно запросить данные от team11.ya-itmo.ru/api

Что делать?

Есть 2 вида запросов на другой источник

  • Простой
  • Непростой

Простые запросы удовлетворяет 2 условиям

  • используют методы GET, POST или HEAD
  • используют простые заголовки
    • Accept
    • Accept-Language
    • Content-Language
    • Content-Type со значением:
      • application/x-www-form-urlencoded
      • multipart/form-data
      • text/plain

Если происходит простой запрос на другой источник, то ответ запроса блокируется браузером (нет предзапроса)

Если происходит непростой запрос на другой источник, то браузер сначала отправит предзапрос (preflight)

Что из себя представляет предзапрос

Это запрос, который использует метод OPTIONS, нету тела запроса и есть 3 заголовка

  • Origin - источник (протокол/домен/порт)
  • Access-Control-Request-Method - HTTP метод непростого запроса
  • Access-Control-Request-Headers - список разделенный запятыми непростых заголовков

Если такой запрос разрешено принимать, сервер должен ответить без тела, статусом 200 и заголовками

  • Access-Control-Allow-Origin - разрешённый источник
  • Access-Control-Allow-Methods - разрешённые методы
  • Access-Control-Allow-Headers - разрешённые заголовки
  • (опциональный) Access-Control-Max-Age - время кеширования разрешения

Cross-Site Request Forgery (CSRF)

(Подделка межсайтовых запросов)

Рассмотрим ситуацию

						
							// мы на странице https://team10.ya-itmo.ru/, где добавлена форма:

							<form action="https://team11.ya-itmo.ru/api/login" method="POST">
								<input type="hidden" name="login" value="itmo">
								<input type="submit" value="Отправить">
							</form>

Что происходит с точки зрения сервиса https://team11.ya-itmo.ru?

Атака использовала слабое звено авторизации - куки позволяют определить, что пришел определенный пользователь, но ничего не говорит об отправляемых данных

(куки отправляются автоматически с запросом)

Игра на внимательность #1

						
							<script>
								fetch('https://team11.ya-itmo.ru/api/mail', {
									method: 'POST',
									// Обеспечивает отправку куки,
									// ассоциированных с team11.ya-itmo.ru
									credentials: 'include',
									headers: {
										'Content-Type': 'application/json'
									},
									// Новый email, который злоумышленник пытается установить
									body: JSON.stringify({ email: 'itmo@mail.ru' })
								});
							</script>

упс, помешает CORS

Игра на внимательность #2

						
							<script>
								fetch('https://team11.ya-itmo.ru/api/mail', {
									method: 'POST',
									credentials: 'include',
									headers: {
										'Content-Type': 'application/x-www-form-urlencoded'
									},
									body: 'email=itmo@mail.ru'
								});
							</script>

Сейчас CORS помешает?

Не помешает - браузер заблокирует ответ, но запрос будет отправлен и принят другой стороной

Как защититься от CSRF?

  • CSRF token
  • Double submit cookie
  • Content-Type based protection
  • Referer-based protection
  • Password confirmation

  • SameSite Cookies

    Set-Cookie: session=value; path=/; SameSite
    SameSite=Strict (куки не отправляются)
    SameSite=Lax (куки отправляются, когда используются безопасные HTTP методы - GET, HEAD, OPTIONS, TRACE)

Насколько серьезны CSRF-уязвимости?

  • Account takeover - атакующий захватывает аккаунт жертвы путем смены email
  • Privilege Escalation - повышение привилегий за счет того, что атакующий через CSRF создает нового пользователя с высокими правами в системе
  • Remote code execution - выполнение кода за счет эксплуатации command injection в админке через CSRF

Может быть такие атаки устарели?

Увы нет, на 2021 год CSRF занимает 10е место в топе уязвимостей (OWASP)

Content Security Policy (CSP)

Политика описывает безопасные источники загрузки ресурсов, устанавливает правила использования встроенных стилей, скриптов

Страница должна содержать заголовок Content-Security-Policy
c 1 или более директив


Базовый вид:

Content-Security-Policy: script-src <source> <source> <source>;

где <source> домен или ключевое слово, например: 'self' или 'unsafe-inline'

Примеры директив:

  • default-src
  • script-src
  • style-src
  • img-src
  • media-src
  • frame-src
  • font-src

default-src применяется для всех неуказанных директив

Еще пример

Content-Security-Policy:
script-src 'self' storage.yandexcloud.net;
style-src 'self' storage.yandexcloud.net;
report-uri: https://team10.ya-itmo.ru/csp/report;

report-uri - адрес, куда браузер автоматически отправит запрос, если сработала CSP

Включение политики CSP на уже рабочем сервисе потенциально опасное изменение


Как быть уверенным, что наша политика CSP ничего не нарушит?

Меняем заголовок Content-Security-Policy на Content-Security-Policy-Report-Only

Что делать, если мы хотим добавить свои inline скрипты/стили, но заблокировать чужие (добавленные злоумышленником)?

Мы не должны указывать в директивах script-src и style-src значения 'unsafe-inline'

						
							// не inline скрипт
							<script src="/js/main.js"></script>

							// inline скрипт
							<script>
								// наша полезная логика
							</script>

Есть 2 способа, как это сделать

  • sha (хеш содержимого скрипта)
  • nonce (атрибут у тега)
						
							// Указываем хеш содержимого скрипта
							Content-Security-Policy: script-src 'self' 'sha256-V8ghUBat8RY1nqMBeNQlXGceJ4GMuwYA55n3cYBxxvs=';

							// inline скрипт
							<script>
								// наша полезная логика
							</script>
							// браузер сам вычислит хеш inline скрипта и проверит, есть ли такое значение в заголовке
						
					
						
							// Указываем хеш содержимого скрипта
							Content-Security-Policy: script-src 'self' 'nonce-randomText';

							// inline скрипт
							<script nonce="randomText">
								// наша полезная логика
							</script>

Clickjacking

Атака, позволяет вредоносной странице кликнуть по сайту-жертве от имени посетителя


Как устроена на практике

  • Посетитель оказывается на вредоносной страницы
  • Кликает по кнопке
  • Поверх этой ссылки вредоносная страница размещает прозрачный iframe с src другого сайта
  • При попытке клика на эту ссылку посетитель на самом деле нажимает на кнопку

Примеры защиты от Clickjacking

  • Выставить заголовок на страницу X-Frame-Options и с помощью него запретить открытие вашего сервиса в iframe
  • Выставить атрибут cookie: samesite

Еще одна отсылка к хакатону


Любые изменения данных на сервере не должны происходить простым запросом (методы: GET, HEAD, OPTIONS, TRACE)

Иначе, например, если добавить картинку в сервис вида <img src="/auth/logout">, пользователь будет разлогинен

Рассылки. Бонусный раздел

Предположим, что у нас есть почта: email@domain.com

Тогда при регистрации на любом из ресурсов указываем не
email@domain.com, а
email+<любой текст>@domain.com

Пример: email+google@domain.com

Теперь в рекламной рассылке можно увидеть почту, куда высылалось сообщение

И теперь у вас есть при одной почте бесчисленное количество адресов
